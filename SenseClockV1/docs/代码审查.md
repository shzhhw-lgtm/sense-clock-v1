## P2：建议本轮修正

### R2. 每分钟时钟依赖 allow-while-idle 闹钟，不能保证休眠中逐分钟准点

- 位置：`app/src/main/java/com/example/senseclockv1/ClockWidgetProvider.kt:36-53,146-162`；`app/src/main/res/values/strings.xml:30-31`。
- 证据：下一分钟始终通过 `setExactAndAllowWhileIdle(RTC_WAKEUP, ...)` 调度；只有闹钟、系统时间变化、插件更新等入口，未见进程存活时的亮屏恢复刷新处理。
- 影响：Android 对 idle 下这类闹钟有频率限制，取得精确闹钟权限不等于能在深度休眠时每分钟触发。长时间息屏后回到桌面可能短暂显示旧时间；当前文字容易让用户以为授权后必定逐分钟准点。实际延迟取决于系统，未在设备上复现。
- 建议：明确休眠限制，评估亮屏/退出 idle 后的补刷策略；动态接收器只能在进程存活时有效，不应宣称能解决所有进程被杀情形。息屏期间尽量减少没有可见收益的重绘唤醒；不要简单改成每分钟用户闹钟来绕过限制。
- 验证：长时间息屏或 Doze、亮屏回桌面、权限撤销、进程回收、重启后，分别检查时间恢复与下一分钟刷新。

### R3. 非数字温度会被当作成功结果覆盖有效天气缓存

- 位置：`app/src/main/java/com/example/senseclockv1/WeatherClient.kt:103-106,161-163`；`WeatherStore.kt:88-94`；`ClockWidgetRenderer.kt:52-66`。
- 触发：天气接口返回成功状态，但 `temp` / `tempMax` / `tempMin` 中含 `--`、`NaN` 等非有效数值。
- 证据：`required()` 只检查非空和不为字符串 null；缓存写入前没有数值校验。渲染器发现任一温度无效后隐藏全部温度。
- 影响：旧的有效缓存被无效数据覆盖，页面却提示更新成功，违背“失败保留缓存”的策略。
- 建议：在构造成功快照前校验三个温度为有限数值；校验失败走已有失败保留缓存路径。
- 验证：模拟非法温度返回，确认旧快照及时间戳不变，显示刷新失败；正常负温、小数温度仍可解析。

### R4. 备用 IP 定位使用明文 HTTP

- 位置：`app/src/main/java/com/example/senseclockv1/WeatherClient.kt:110-115`；`app/src/main/res/xml/network_security_config.xml:4-7`。
- 触发：首选 IP 定位或其城市查询失败，进入 `lookupFallback()`。
- 影响：该响应未经 TLS 保护，同一网络中的攻击者可篡改返回城市，使天气绑定错误位置。此请求没有携带和风 API Key，因此不能据此声称 Key 被明文泄漏。
- 建议：换用实际支持 HTTPS 的定位服务，或删除明文备用并提示用户使用固定位置；同步删除域名明文放行。不能只机械把 URL 改为 HTTPS 而不确认服务支持。
- 验证：首选服务失败时检查备用/固定位置路径以及已有缓存保留。

### R5. 仪器测试断言与当前缓存策略冲突

- 位置：`app/src/androidTest/java/com/example/senseclockv1/ClockWidgetRenderTest.kt:61-66`；`app/src/main/java/com/example/senseclockv1/WeatherClient.kt:42-52`。
- 证据：测试构造 25 小时前的有效快照，断言 `WeatherSnapshot.fromJson(...) == null`；当前解析函数不检查年龄，会返回该快照。
- 影响：这条断言从静态逻辑即可确认不符合当前实现，运行到此应失败，也使后续天气素材遍历在此测试中无法执行。本次未运行测试，不记作实测失败。
- 建议：以当前“过期缓存保留并标注”的产品行为为准，修改断言，并补充过期提示逻辑的检查；不要为旧测试删除离线缓存功能。
- 验证：手动执行修正后的对应仪器测试。

### R6. 后台刷新重复请求完整插件重绘

- 位置：`app/src/main/java/com/example/senseclockv1/WeatherStore.kt:93,101`；`WidgetWeatherJob.kt:35-39`；`ClockWidgetProvider.kt:56-71,115-137`。
- 证据：天气更新成功和普通失败都由 WeatherStore 请求一次刷新，Job 的 finally 再请求一次；单线程 executor 为每次广播排队执行完整 `updateAll()`，没有合并重复任务。
- 影响：一次实际天气请求通常导致两轮全部插件渲染；失败时即使数据没更新仍会重复。快速切换主题也会不断排队。增加图片生成、裁剪、内存分配和跨进程传输成本。
- 建议：让一个层负责天气结果的重绘通知；若缓存命中需要刷新也单独处理，避免漏刷新。必要时合并连续重绘请求，只保留最新状态，不改分钟调度可靠性。
- 验证：记录一次后台刷新对应的渲染次数，并确认成功、失败、缓存命中均仍能正确显示。

### R7. 预览已变为固定示例，但页面仍把真实更新结果紧邻显示

- 位置：`app/src/main/java/com/example/senseclockv1/MainActivity.kt:125-142,172-175,274-315`；`app/src/main/res/values/strings.xml:15,18,26`。
- 证据：预览只选择静态资源，不读实际 weather；下面显示真实更新时间和“天气已更新”状态，没有注明图中城市、时间、温度为示例。widget_name 的值“时钟权限设置”同时用于插件列表名称及预览无障碍描述。
- 影响：用户刷新天气后仍看到固定城市温度，容易误判刷新失败；桌面插件列表名称和屏幕阅读器描述也不符合内容。
- 建议：增加“主题效果示意，时间与天气为示例”说明；需要呈现实际天气时用简洁文字展示。拆分插件名称、权限卡片标题和预览描述资源。
- 验证：首次安装、配置不同城市、刷新成功后，用户能明确区分示意图与真实天气状态；检查插件选择器与 TalkBack。

## P3：非阻断优化

### R8. 预览图片缓存随进程常驻，缺少内存预算

- 位置：`app/src/main/java/com/example/senseclockv1/MainActivity.kt:302-306`。

### 🟡 建议修改

**R10. 每次 Activity 回到前台都会触发完整小部件重绘**

- 位置：`app/src/main/java/com/example/senseclockv1/MainActivity.kt:31-36`
- 问题：`onResume()` 无条件调用 `ClockWidgetProvider.requestUpdate(this)`。只要用户从设置、其他应用或系统页面返回，即使主题、时间和天气都没有变化，也会发送重绘广播。
- 性能影响：小部件会重新创建 Bitmap、执行透明边界扫描并通过 `RemoteViews` 更新，属于可避免的后台 CPU、内存和跨进程开销。
- 建议：删除 `onResume()` 中的无条件 `requestUpdate()`；保留 `ClockWidgetProvider.requestUpdate()` 在主题、时间制式、天气成功/失败和系统时间变化等真正发生状态变化的路径。若需要前台回归刷新，只在检测到配置或天气状态变化时触发。

**R11. 每分钟小部件渲染都会分配像素数组并扫描整张 Bitmap**

- 位置：`app/src/main/java/com/example/senseclockv1/ClockWidgetRenderer.kt:38-40,70-103`
- 问题：每次 `render()` 都创建完整 Bitmap；`trimTransparentBorder()` 随后创建 `IntArray(width * height)`，逐像素扫描整张图片，再可能创建裁剪 Bitmap。
- 性能影响：小部件每分钟刷新时会产生较大的临时内存和 CPU 峰值；多个小部件或较大尺寸下会线性放大。当前单线程执行器保证了安全，但不能降低单次渲染成本。
- 建议：优先使用固定内容边界，去掉逐像素透明边界扫描；如果必须保留裁剪，至少缓存固定布局的裁剪范围，或复用可增长的像素缓冲区并按尺寸限制。修改前应在低端设备和多个小部件场景确认 Bitmap 内存峰值。

**R12. 单次小部件广播对不同尺寸逐个完整渲染，缺少合并策略**

- 位置：`app/src/main/java/com/example/senseclockv1/ClockWidgetProvider.kt:56-71,92-137`
- 问题：连续的 `ACTION_REDRAW` 广播会在单线程执行器中排队；`updateAll()` 对每个小部件都执行完整渲染，即使短时间内多个请求使用同一主题、时间格式和尺寸。
- 性能影响：快速切换设置、天气更新和系统事件叠加时，旧状态的渲染仍会全部执行，增加队列延迟和 Bitmap 分配。
- 建议：按渲染参数分组复用 Bitmap，或在执行器入口合并短时间内的重复刷新请求，只保留最新一次状态；每个小部件仍需单独调用 `updateAppWidget()`。

**R13. 网络响应使用 `readText()`，没有响应体大小上限**

- 位置：`app/src/main/java/com/example/senseclockv1/WeatherClient.kt:186-201`
- 问题：HTTP 响应通过 `readText()` 一次性读入内存。当前接口正常响应很小，因此不是当前的主要性能瓶颈，但服务异常或代理返回超大内容时会造成不必要的内存增长。
- 建议：为响应体设置合理上限，超过上限立即中断并转入现有错误处理；天气和定位接口只需几十 KB 级别的响应预算。
